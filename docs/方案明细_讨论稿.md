## 1. 一条消息的完整生命周期

```
①群有新消息
   │  （三机制发现：红点 / 免打扰小圆点 / 定时轮询）
   ▼
②切入该群  ── 抓图 OCR 顶栏校验，防切错群
   ▼
③补读      ── 找「以下为新消息」分界线，找不到就向上翻页
   ▼
④解析气泡  ── 分左右 + 绑定发送者昵称 + 标出图片气泡
   ▼
⑤取图      ── 点开图片 → 抓预览窗 → 存原图 → Esc 关闭 → 校验已关
   ▼
⑥识别      ── 云端视觉大模型出明细 + 合计数
   ▼
⑦校验      ── Σ(单价×数量)+运费-优惠 == 截图合计；数字必须在 OCR 原文中出现
   ▼
⑧算价      ── 报价 = 截图合计 × 0.95，四舍五入到分
   ▼
⑨拦截判定  ── 任一条不过 → 转人工，不发
   ▼
⑩发送      ── @发起人 → 金额文本 → 图片 → 差分验收
   ▼
⑪落库      ── 幂等键、原图、识别过程、金额、发送状态 → 进报表
```

## 2. 模块明细

### 2.1 群发现与白名单

**做法**

- 配置文件维护群名单（群名 + 可选备注别名）
- 匹配前先**剥离人数后缀**：`正则 [\(（]\d+[\)）]\s*$` → `"五常大米下单群(128)" → "五常大米下单群"`
- 匹配用「剥离后全等」，不模糊匹配。原仓库 `normalize_for_match()` 把 `0→o`、`1→l`，群名里带数字时有害，必须收窄。

| 参数 | 建议值 |
|---|---|
| 人数后缀剥离 | 必做 |
| 匹配方式 | 剥离后全等（可配忽略全半角/空格） |

**失败处理**：群名匹配不上（改名了）→ **告警**，不静默跳过。原仓库最危险之处就是静默跳过，你不知道漏了。

**已实现（`src/groups.py` + `config/groups.json`）**

```bash
python src/groups.py --list                  # 看当前配置
python src/groups.py --test "五常大米下单群(128)"   # 试一个群名
python src/groups.py --selfcheck             # 跑内置用例（9 条，全通过）
```

- 三种模式：`whitelist`（只回列出的群，默认）/ `blacklist`（排除列出的）/ `all`（全部，不推荐）
- 归一化用 `NFKC`，全角括号、全角数字、群名中间空格都能正确对齐，避免 OCR 认错全半角导致失配
- 排除词优先级高于白名单（如群名含「测试」「内部」一律不处理）
- 每条判定都带 `reason`，写进日志，便于事后查"为什么这个群没回"

### 2.4 补读翻页（新增，决定"不漏"）

**核心发现：微信自带未读分界线**

打开有未读的群时，消息列表里会插入系统提示 **「以下为新消息」**。原仓库的解析器已把这行加进忽略词（L523）——因为它干扰文字识别被过滤掉了。但它恰恰是最可靠的补读边界：**下面全是未读**。

比"找自己上一条发言"可靠得多：群里可能几小时没说话，找自己消息要翻很多屏。

**做法**

```
切入群 → 抓图 → OCR 找「以下为新消息」
  ├─ 找到 → 只处理该行以下的气泡 ✔
  └─ 没找到（纯图片消息可能读不到该行）
       → 向上翻一屏 → 再找 → 最多 5 屏
       → 仍找不到 → 回退：用「最后一条我方绿底气泡」作边界
```

**翻页实现**（优先第一条）

| 方式 | 做法 | 可靠性 |
|---|---|---|
| PageUp 键 | 先点聊天区获得焦点 → `keybd_event` 发 PageUp | 高（Qt 原生响应） |
| WM_MOUSEWHEEL | `PostMessage(hwnd, 0x020A, delta<<16, 屏幕坐标)` | 中（Qt 对 PostMessage 滚轮不稳） |

> `WM_MOUSEWHEEL` 的 lParam 是**屏幕坐标**，不是客户区坐标；wParam 高 16 位是 delta（每格 120）。原仓库 `post_click_client_point` 用客户区坐标，两者不可混用。

**三条硬约束**

1. **已读游标**：每群维护"上次处理到哪"，翻到游标之前即停
2. **`finally` 回底**：无论成败必须滚回底部，否则下次从历史开始，大面积误读
3. **翻页期间独占**：翻页是全局界面状态操作，禁止与其他会话调度并发

| 参数 | 建议值 |
|---|---|
| 单次最大翻页 | 5 屏 |
| 每屏停留 | 0.3 s |
| 翻页失败 | 记 FAILED，下轮重试，不丢弃 |

### 2.5 已读游标

OCR 结果每次微差，文本 hash 不稳。分类型设游标：

| 消息类型 | 游标 | 说明 |
|---|---|---|
| 图片消息 | **图片内容 sha256** | 最稳，同图 hash 不变 |
| 文字消息 | 群+发送者+去标点文本 归一化 hash | 辅助 |
| 群级 | 最后处理的时间戳 + 位置 | 兜底 |

订单都是图片，**图片 hash 天然幂等**，这是本场景的幸运之处。

### 2.6 气泡解析（群版，需重写）

原仓库只输出 `(是否对方, 文本)`，群聊不够用。

```python
{
  "type": "text" | "image" | "system" | "divider",
  "side": "in" | "out",
  "sender": "张三" | None,
  "y_top": 1234, "y_bottom": 1300,
  "text": "...",
  "image_box": (x1,y1,x2,y2),
  "confidence": 0.93,
}
```

**图片气泡识别**

特征：该区域无 OCR 文字 + 连续非背景色矩形 + 高度 > 80px。

方法：以 OCR 文字框为占位，在聊天区找**面积 > 阈值且未被文字框覆盖**的连续非背景色区块。

**误判源**：表情包、链接卡片、小程序卡片。过滤：宽高比异常（很扁的卡片）或高度 < 80px 的排除。

### 2.7 群内发送者归属

微信群内：同一人连发合并气泡；不同人之间显示**昵称行**（小字灰色，气泡左上）。

```
昵称行「张三」 y=1200
  气泡 y=1230-1500   ← 张三
  气泡 y=1510-1700   ← 张三（连发无昵称行）
昵称行「李四」 y=1750
  气泡 y=1780-2000   ← 李四
```

用 OCR 找昵称行 y 坐标，其下气泡归属该昵称；找不到则沿用上一条。

**失败降级**：`sender=None` → 仍处理订单，回复不带称呼、**不 @**。宁可少个称呼，不能漏单。

### 2.8 图片抓取（决定识别精度）

聊天内缩略图仅 200-300px，订单金额必糊。必须拿大图。

```
① 定位图片气泡 box
② box 中心 PostMessage 单击（微信单击图片即打开预览）
③ 轮询窗口列表，找 Weixin.exe 下新增的窗口（预览窗），超时 1.5s 判失败
④ 抓预览窗 → 存 PNG
⑤ 校验：尺寸 > 400px、非全黑、宽高比正常
⑥ Esc 关闭
⑦ 轮询确认预览窗已消失（超时 1s）；未消失 → 再 Esc → 仍不消失 → 中止本群告警
```

**`try/finally` 强制关闭**：任何异常都必须走关闭。预览窗不关，后续 OCR 全读错界面，会连锁误判。

**第一版不做**"查看原图再抓一次"，先用预览窗尺寸验证精度是否够。

**备选（暂不采用）**：读微信本地图片缓存目录。4.x 缓存位置与加密已变，且属读取客户端数据，边界更模糊。

### 2.9 识别（云端视觉大模型 + OCR 校验）

**通道 A：云端视觉大模型**（已定 D2）

严格 JSON 输出：

```json
{
  "is_order": true,
  "items": [
    {"name": "五常稻花香大米", "spec": "5kg", "qty": 2, "unit_price": 59.90, "subtotal": 119.80}
  ],
  "shipping": 0.00,
  "doc_discount": 0.00,
  "total": 119.80,
  "confidence": {"items": 0.92, "total": 0.97},
  "uncertain_fields": []
}
```

**通道 B：传统 OCR**

只干一件事：吐出截图里所有文字与数字，用于核对通道 A 的关键数字是否真的出现过。

**校验逻辑（任一不过即拦截）**

1. `total` 必须能在通道 B 文本中找到（容忍 `119.80`/`119.8`/`￥119.8`）
2. 每个 `unit_price` / `subtotal` 同上
3. 找得到不 → 判"编造"，拦截
4. `uncertain_fields` 非空 → 拦截
5. 算术闭环不成立 → 拦截（见 2.11）

**为什么必须两通道**：视觉大模型会**编造数字**（看起来很合理的幻觉），图片越糊越容易。OCR 原文是唯一能证明"这数字真在图上"的证据。

**云端的数据边界**：截图会上传到模型服务商。需在合同/告知层面确认合规；建议①只上传裁剪后的订单截图区域②不上传整屏③服务商选承诺不用于训练的。

### 2.10 明细校验（不再需要价目表）

**v0.2 重大简化**：报价只用"截图合计"，所以**废除价目表、SKU 别名表、单位换算表**——原方案里最大的运营坑直接消失。

但**明细仍然要识别**，因为它是校验总价的唯一手段：

```
Σ(单价 × 数量) + 运费 - 单据优惠  ==  截图合计（容差 0.02 元）
```

- 相等 → 说明每行都识别对了，总价可信
- 不相等 → 说明有漏识别的行、或单据有额外费用没识别到 → **转人工**

这样既砍掉运营负担，又保住交叉验证。**这是本方案最划算的一次范围收缩。**

### 2.11 算价（折扣规则）

```
商品金额 = 截图合计 - 截图运费          （默认运费不参与打折，见 Q-a）
报价     = 商品金额 × 0.95 + 截图运费
报价     = 四舍五入到分（ROUND_HALF_UP）
```

**三条硬规则**

1. **金额一律用整数「分」计算**（int 或 Decimal），**绝不用 float**。`0.1+0.2 != 0.3` 在钱上是事故。
2. **折扣系数配置化**，不写死。促销期改配置即可。
3. **必须与截图合计对账**：算的基数取自截图合计，需同时通过 2.10 的明细校验。

**回复文案**（关键：把原价和折后价都写出来，避免纠纷）

```
张三，订单合计 119.80 元，95 折后 113.81 元
```

### 2.12 发送（@ + 文本 + 图片）

**顺序**

```
① @ 发起人（见 2.16，可降级为不 @）
② 金额文本 → Ctrl+V → Enter → 差分验收
③ sleep 0.6s
④ 图片 → 剪贴板 CF_DIB → Ctrl+V → Enter → 差分验收
```

**为什么分两次发**：微信一次粘贴只能带一种内容。分两次且留间隔，避免被吞。

**图片写剪贴板**：`CF_DIB`（BITMAPINFOHEADER + bottom-up BGR）。ctypes 调 `GlobalAlloc`/`SetClipboardData`。不能传文件路径（那会当文件发）。

**发送后验收**：沿用原仓库 `verify_diff_bubble_success()`，比对前后绿底气泡增量，返回三态。

> **返回"不确定"时按已发送处理并告警，不重试。** 重试才是重复报价的真正来源。

### 2.16 @ 发起人（新增，需单独验证）

真 @ 是整个方案里除抓图外第二个"必须实机验证"的点。原理：输入框输入 `@` → 弹出成员列表 → 选中 → 变成 mention 芯片 → 再输入正文。

**分层降级设计**（每层失败退下一层，**绝不因 @ 失败而不发消息**）

| 层级 | 做法 | 失败判据 |
|---|---|---|
| L1 | 焦点输入框 → 输入 `@` → 等 0.4s 弹窗 | 抓图检测不到弹窗 |
| L2 | 输入昵称前缀过滤列表 | — |
| L3 | `Enter` 选中列表首项 | 输入框未出现 mention 芯片 |
| L4 | OCR 定位弹窗 → 找到昵称行 → PostMessage 点击 | 点击后仍无芯片 |
| L5 | **降级：文本里写「张三，…」**，不 @ | — |

**@ 成功的验证信号**

发送后，自己的绿底气泡里 @ 的昵称会显示为**蓝色高亮**。检测绿底气泡内是否出现蓝色文字区域 → 有则 @ 成功。这是可自动验证的硬信号，不靠猜。

**已知风险**

| 风险 | 处理 |
|---|---|
| **群内同名** | 无法确定是哪个 → 直接走 L5 降级不 @，并告警 |
| 昵称含 emoji / 特殊符号 | 前缀过滤可能失效 → 走 L4 OCR 点选 |
| 成员太多，弹窗需滚动 | 第一版不处理，走 L5 降级 |
| 输入法状态影响 `@` 输入 | 优先用剪贴板粘贴 `@`，不行再 `keybd_event` Shift+2 |
| 弹窗遮挡/位置不定 | 靠 OCR 全局找昵称文字，不依赖固定坐标 |

**必须先做的小实验**（在抓图打通之后）：单独写个脚本，只测"输入 @ → 弹窗出现 → Enter 能否选中 → 输入框出现芯片"，不发送。三步验证完再写进主流程。

### 2.13 幂等

**键**：`group_id + sender + image_sha256`

- 发送前查库，已 `SENT` → 跳过
- 状态机 `NEW → PARSED → OCR_DONE → VALIDATED → PRICED → SENDING → SENT / HELD / FAILED / UNKNOWN`
- **`SENDING` 超时（30s 未变 SENT）→ 标 `UNKNOWN`，告警，不自动重发**
- 进程重启从 DB 恢复，不重发

> 原仓库去重状态在内存（L101 `LAST_PROCESSED_SIGNATURE`），重启即丢，会重复报价。必须修掉。

### 2.14 转人工

### 2.15 限速

| 维度 | 建议 |
|---|---|
| 全局发送间隔 | ≥8 s，±3 s 随机 |
| 单群每小时 | ≤30 条 |
| 连续发送 | 20 条后冷却 60-120 s |
| 夜间 | 23:00-07:00 降频或暂停 |

> 注意：@ 会额外触发弹窗与选择动作，单条耗时比纯文本多 0.5-1.5 秒，限速要按 @ 版本重新标定。
