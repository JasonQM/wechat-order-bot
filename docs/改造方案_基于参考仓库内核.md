## 0. 结论修正

前一份文档判「可复用 0 行」，**这个判断过重，予以修正。**

正确结论是：**窗口操作层可以直接当骨架（约 600 行有效资产），感知层与业务层需重写。**

关键在于把两件事拆开算，之前我把它们混在一起判了：

| 维度 | 协议层（iPad 协议） | 屏幕层（本仓库路线） |
|---|---|---|
| 功能上限 | 高（结构化消息、原图、离线补偿） | 中（受 UI 与可见区域约束） |
| 工程成本 | 低（SDK 现成） | 高（要自己造采集与补读） |
| 特征检测风险 | 中高（走非官方协议接口） | 低（无注入、无内存改写） |
| 行为风险 | 中 | 中（两者相同，见第 5 节） |

**选择屏幕层 = 用工程成本换账号的"技术特征安全"。** 在「真实客户群 + 每天 100-500 单 + 封号即业务中断」这个前提下，这个交换是成立的，甚至可能是更理性的那个。

## 4. 三个真正的难点

### 4.1 向上翻页补读（决定"不漏"）

这是全方案唯一无法绕过的硬骨头。屏幕架构下，**群消息一旦被顶出可见区，就只能靠滚动加载回来**。

可行方案：向聊天区域 `PostMessage` `WM_MOUSEWHEEL`（或发送 `PageUp`），每次加载一屏，逐屏向上找，直到：

- 找到自己上一条绿底消息 → 停止（说明再往上是已处理区）
- 或达到最大翻页次数（防死循环）

**必须配套的三条硬约束：**

1. **已读游标**：为每个群维护"最后处理到的消息指纹"，落库。翻页时遇到游标之前的消息直接跳过。
2. **`finally` 回底**：无论成功失败，必须滚回最底部。否则下一次处理会从历史位置开始，导致大量误读。
3. **翻页期间禁用其他调度**：翻页是全局界面状态操作，不能和其他会话切换并发。

### 4.2 图片气泡抓取（决定"识别精度"）

截图里的订单信息要准确，必须拿到**大图**，不能拿聊天窗口里的缩略图（约 200-300px，数字必糊）。

流程：

```
检测图片气泡 → 双击打开大图预览窗 → PrintWindow 抓预览窗（高清）→ 保存 → Esc 关闭 → 校验已关闭
```

**风险点：**

- 点错目标（点到头像、点到引用）→ 抓图前必须校验预览窗标题/尺寸
- 关闭失败 → 后续 OCR 全部读到错误界面 → **`try/finally` 强制 Esc，并校验窗口已消失**
- 预览窗尺寸不代表原图尺寸，可能需要点"查看原图"再抓一次

### 4.3 群内发送者归属（决定能否 @ 对的人）

屏幕架构只能靠视觉线索：

- 微信群内，同一人连发会合并气泡，不同人之间会显示**昵称行**
- 用 OCR 读昵称行 → 把其下方的气泡归属给该发送者
- 昵称行识别失败时，**降级为不 @**，但仍然处理订单（宁可少一个 @，不能漏单）

## 5. 修正「零封号风险」这个说法

仓库 README 写「100% 外部感知无注入，零封号风险」。这个说法**不准确，必须拆开看**：

| 风险类型 | 屏幕方案 | 说明 |
|---|---|---|
| **特征风险**（DLL 注入、内存改写被检测） | ✅ 显著降低 | 不碰微信进程内部，这是真实优势 |
| **行为风险**（发送频率、内容重复、群发特征、账号活跃曲线） | ❌ **不降低** | 服务端看到的是"这个号在高频发消息"，与你用鼠标还是用代码发的无关 |

**准确表述：特征风险显著降低，行为风险不变。** 因此限速不是可选项，是必需项。

建议的限速参数（保守起点，按实际调整）：

- 全局：相邻两条发送间隔 ≥ 8 秒，带 ±3 秒随机
- 单群：每小时 ≤ 30 条
- 夜间（23:00-07:00）：暂停或降频
- 连续发送 20 条后强制冷却 1-2 分钟

## 6. 吞吐预算

单条闭环耗时：

| 环节 | 耗时 |
|---|---|
| 抓图 + OCR | 0.5 - 1.5 s |
| 订单识别（视觉大模型） | 2 - 5 s |
| 算价 + 校验 | < 0.1 s |
| 发送 + 差分验收 | 0.5 - 0.9 s |
| **合计** | **约 3 - 7.5 s / 条** |

对 100-500 单/天、集中在 8 小时营业时段：

- 平均需求：57 秒/单 → **有充足余量**
- 峰值（例如 10 单集中在 2 分钟）：需排队约 60-75 秒 → **可接受，但要给用户提示**
- 结论：**吞吐不是瓶颈，瓶颈是补读与识别的正确性**

## 7. 实施顺序

| 阶段 | 内容 | 验收 | 是否阻断后续 |
|---|---|---|---|
| **S0** | 抓图可行性验证（`tools/probe_wechat.py`） | 4.1.15 上 PrintWindow 能抓到清晰完整画面 | **是，生死点** |

| **S1** | 群接入 + 队列调度 + 翻页补读 | 5 个群连续 2 小时不漏单 | 是 |
| **S2** | 图片气泡抓取 | 抓到的图能看清订单数字 | 是 |
| **S3** | 订单识别 + 算价 + 双通道校验 | 标注集准确率达标，错误全被拦截 | 是 |
| **S4** | 幂等 + 发送图片 + 限速 | 7 天无重复报价、无漏单 | 否 |

> **S0 不通过就不要往下走。** 如果 4.1.15 的 `PrintWindow` 抓不到画面（可能因为硬件加速渲染），这条路线直接作废，必须回到协议层方案——那时候的选择不是"成本高低"，而是"有没有"。
