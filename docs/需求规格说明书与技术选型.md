## 0. 结论摘要

1. **参考仓库不可用，也不建议在其上改造。** 它的核心设计目标是"阻断群聊"，与需求方向相反；图片消息链路完全缺失；整窗 OCR 前把图缩到 1000px 宽，与"识别金额不能出错"直接冲突。可复用代码为 0 行。
2. **"必须个人微信"+"每天 100-500 单"这两个前提同时成立，屏幕自动化路线整体出局**，只能走协议层。
3. **当前个人微信可编程的现实路线只有一条主线**：Wechaty + PadLocal（iPad 协议），或等价的商业协议 API 服务商。hook 类方案（WeChatFerry 等）已停止维护且不支持微信 4.x，不具备生产条件。
4. **"不能出错"在工程上无法用"100% 自动发送"兑现。** 只有"识别不确定就不发、转人工"才能兑现。这是本方案的第一条设计原则。
5. 最大的风险不是技术，是**封号**。必须先接受风险对策（专用号、限速、客户联系方式独立备份、备用号切换），再谈开发。

## 1. 需求确认

### 1.1 已确认

| 维度 | 结论 | 影响 |
|---|---|---|
| 承载平台 | **个人微信**，不接受迁移到企业微信 | 排除官方 API，只能走第三方协议层 |
| 业务场景 | 多个微信群里，群成员发订单截图 | 需要群消息接入 + 发送者身份 + 图片消息 |
| 处理动作 | 识别截图信息 → 计算订单金额 → 回复金额文本 + 一张固定图片 | 需要"发图"能力，不是纯文本机器人 |
| 出错策略 | 不确定时先用大模型二次识别，仍不确定**转人工** | 支持"宁可漏答不可错答"的降级路径 |
| 日处理量 | 100-500 单/天 | 峰值约 1 单/分钟，需要队列与幂等，屏幕方案扛不住 |

### 1.2 待确认（阻塞开发，需甲方回答）

| # | 问题 | 为什么必须问 |
|---|---|---|
| Q1 | **订单截图的版式是否统一？** 是来自同一个下单系统（固定版式），还是各家各户随手截（版式全乱）？ | 这是成本分水岭。版式固定可用模板定位，成本低、准确率高；版式全乱必须全靠视觉大模型 + 高比例转人工，成本翻倍 |
| Q2 | 回复时**是否需要 @ 发起人**？ | 影响协议层选型（必须能拿到群成员昵称）与回复文案模板 |
| Q3 | **具体几个群？每个群多少成员？** 群的活跃时间段？ | 决定限速策略、并发模型、是否需要多账号分流 |
| Q4 | **回复时限**要求是多少秒内？ | 决定是否可以走"二次识别"这条重链路 |
| Q5 | 金额计算的**依据**是什么？价目表从哪来、谁维护、多久变一次？ | 决定规则引擎的形态（配置文件 / 后台管理 / 数据库） |
| Q6 | 那张**固定图片**是什么？收款码、价目表、还是店铺介绍？是否需要按群/按商品区分？ | 影响发送逻辑（可能需要多套图片） |
| Q7 | 是否需要**留痕与对账**？（每单原图、识别结果、金额、发送状态可查） | 影响是否要建库与后台，工作量差异大 |
| Q8 | 转人工的**通知渠道**？微信通知自己 / 手机 App / 电脑弹窗？ | 决定人工确认环节的实现方式 |

> **Q1 是最关键的一条。建议先提供 20-30 张真实截图样本，我据此给出识别准确率的可行性判断。** 没有样本，任何准确率承诺都是空话。

## 2. 参考仓库评估结论

### 2.1 需求能力对照

| 需求 | 仓库现状 | 判定 |
|---|---|---|
| 接入多个群的群消息 | `is_group_chat_name()`（L371-386）识别群名，`is_name_matched_strict()`（L401-403）直接 `return False`；即使关白名单，`is_valid_non_whitelist_target()`（L1010）再拦一次 | ❌ 被硬阻断 |
| 不漏消息 | 单窗口单会话；全文无侧边栏滚动逻辑；`extract_pending_incoming_messages()`（L573-595）只读当前可见气泡；去重状态 `LAST_PROCESSED_SIGNATURE`（L101）仅驻内存 | ❌ 架构不支持 |
| 拿到截图原图 | `parse_chat_bubbles_chromatic()`（L496-571）只处理 OCR 文本块，图片消息无文本即被忽略 | ❌ 完全缺失 |
| 识别订单字段 | OCR 前先缩放到 1000px 宽（L984-991）；聊天内缩略图仅 200-300px 宽 | ❌ 精度不可用 |
| 计算金额 | 无任何计价逻辑 | ❌ 完全缺失 |
| 回复文本 | 剪贴板 + Ctrl+V + Enter（L852-933） | ✅ 可借鉴思路 |
| 回复图片 | 无 | ❌ 缺失 |
| 知道消息是谁发的 | 只区分"左=对方 / 绿=我方"（L552），群内无法区分成员 | ❌ 完全缺失 |

### 2.2 三个根本性缺陷

**缺陷一：把群聊当作要防御的对象。** 这是它的核心安全模型，不是遗漏。拆掉这层防火墙，它用来防串发的最后一道保险也一并失效。

**缺陷二：「不漏消息」在屏幕架构里物理上不可能。** 群消息一多就被顶出可见屏，信息在屏幕上已经不存在，改代码也捞不回来。免打扰群的红点表现不一致，会被静默跳过且不报错。

**缺陷三：图片来源被自己的架构掐死。** 微信内图片是渲染出来的缩略图，没有"下载"动作。即便补上"点开大图→抓预览窗→关闭"，输入质量仍然是全链路最差的一环。把最需要精度的环节放在最差的输入源上，方向就错了。

### 2.3 复用边界

- **可复用代码：0 行。**
- **可借鉴的工程思路：3 条**——发送后二次校验、白名单硬熔断、连发消息聚合。这三点在协议层方案中由 SDK 回执与消息队列天然满足，无需移植。

## 3. 目标架构

```
群消息 ──► ① 协议网关 ──► ② 原图下载+落库 ──► ③ 双通道识别+交叉校验
                                                      │
                                                      ▼
                                          ④ 算价 + 算术闭环复核
                                                      │
                                        ┌─────────────┴─────────────┐
                                        ▼                           ▼
                              置信达标：自动回金额+图片      不达标：转人工确认
```

### 3.1 采集层（决定"不漏"）

- 多个指定群的消息全量接入，**不依赖任何 UI 红点**
- **支持离线补偿**：断线、重启、服务中断期间的消息能拉回（这是"不漏"唯一可靠的来源）
- 每条消息必须携带：群 ID、发送者 wxid、发送者昵称、消息类型、时间戳、消息唯一 ID
- 图片消息直接取得**可下载的原图**，不经过任何缩放
- **幂等键落库**：`群ID + 发送者 + 图片内容hash`，重启不重发

### 3.2 识别层（决定"不错"）

见第 5 节，这是本方案的技术核心。

### 3.3 业务层

- 价目表 / 规则可配置（商品、规格、数量阶梯价、折扣）
- 计算结果与截图中的"合计"做**对账**，不一致即拦截
- 全链路留痕：原图、OCR 原文、模型原始输出、计算过程、最终金额、发送状态

### 3.4 输出层

- 回复格式：金额文本 + 固定图片
- 群内可选 @ 发起人
- 发送失败重试与重复发送熔断

### 3.5 运行层

- 拟人化限速（消息间隔随机化、单群每小时上限、夜间静默）
- 掉线告警、封号告警、备用号切换预案
- 转人工的待办入口

## 4. 技术选型对比

### 4.1 方案矩阵

| 方案 | 多群接入 | 图片原图 | 离线补偿 | 维护状态（2026-11） | 成本 | 封号风险 | 结论 |
|---|---|---|---|---|---|---|---|
| **Wechaty + PadLocal（iPad 协议）** | ✅ 完整 | ✅ 支持 | ✅ 登录态持久化，重启免扫码 | 在用主力方案，需核实最新版本 | 按周期付费 token（有试用） | 中 | **推荐主线** |
| **商业协议 API 服务商** | ✅ | ✅ | ✅ | 取决于服务商 | 按量/包月 | 中（风险转移给服务商） | **备选，适合不想自己维护网关** |
| WeChatFerry 类 hook | ✅ 理论支持 | ✅ | ⚠️ | ❌ **已停止维护**，锁定微信 3.9.x 特定小版本，**不支持微信 4.x** | 免费 | 高 | **排除，不具备生产条件** |
| 屏幕自动化（参考仓库路线） | ❌ 单会话 | ❌ | ❌ | 个人项目 | 免费 | 低（但功能不成立） | **排除** |
| 企业微信官方 API | ✅ | ✅ | ✅ | 官方维护 | 认证费用 | 无 | 已排除（甲方要求个人微信） |

### 4.2 为什么主线是 iPad 协议

- **与 PC 微信客户端版本解耦。** hook 类方案最大的死穴是"微信一升级就失效"，而 iPad 协议走的是服务端接口，不受 PC 客户端版本影响。在微信 4.x 全面铺开的当下，这一点是决定性的。
- **群能力完整**：群消息、@成员、群成员昵称、入群离群事件。
- **消息类型覆盖全**：文本、图片、文件、视频、语音、小程序，图片可直接获取。
- **登录态可持久化**，长期挂机不需要反复扫码。

### 4.3 选型前必须核实的三件事

1. **PadLocal 当前的维护状态与报价**——社区资料显示按其周期付费、有短期试用，但价格与可用性可能变动，**采购前必须以官方渠道现价为准**。
2. **是否支持你所用的账号类型**（新注册号、有风控记录的号可能无法登录第三方协议）。
3. **服务商的 SLA 与数据合规条款**——消息内容会经过第三方网关，涉及客户订单信息，需确认数据是否落库、保留多久。

## 5. 识别链路设计（核心）

### 5.1 双通道交叉校验

| 通道 | 角色 | 输出 |
|---|---|---|
| A. 视觉大模型（多模态） | **主力**。版式不统一场景下的唯一可行解 | 结构化字段 + 每字段置信度 |
| B. 传统 OCR | **校验**。只用于核对关键数字 | 原始文本 + 位置 |

**为什么不用传统 OCR 当主力**：OCR 只给文本框和文字，没有可靠的字段级置信度，**它不会告诉你它错了**。版式一变就要重写模板，维护成本失控。视觉大模型能直接吐结构，且能对"看不清"表态。

### 5.2 拦截规则（任何一条不过 → 不发）

1. 金额字段置信度低于阈值
2. 通道 A 与通道 B 的关键数字不一致
3. 易混字符（`1/7`、`0/O`、`8/B`、`6/5`、`3/8`）出现多候选
4. 算术闭环不成立（见 5.3）
5. 识别出的商品不在价目表中
6. 金额超出合理区间（如单笔上限）

命中任一条 → **第二次识别**（换模型 / 提高分辨率重跑）→ 仍不过 → **转人工，不发**。

### 5.3 算术闭环

```
单价 × 数量 = 小计
Σ(小计) - 折扣 = 总计
总计 == 截图上的合计
```

四个数字互相印证，任一环节对不上即拦截。**这一条能拦住绝大多数错误，且实现成本极低，性价比最高。**

### 5.4 幂等与防重发

- 幂等键：`群ID + 发送者wxid + 图片内容hash`，落永久存储
- 发送前查库，已发过则跳过
- **进程重启不得导致重复报价**——这是参考仓库的严重缺陷（内存态去重），必须避开

### 5.5 转人工

- 推送给人工：原图 + 模型识别结果 + 各字段置信度 + 计算过程
- 人工一键确认后由系统代发（保留发送记录）
- 待办积压超阈值时告警

## 6. 关键风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| **微信号被封 / 限制登录** | 中高（量级不低） | 业务中断、客户关系丢失 | 专用号与主号隔离；拟人化限速；只在你指定的群活动，不主动加人、不群发；**客户联系方式独立备份**；备用号 + 快速切换预案 |
| 协议服务商停服 / 涨价 | 中 | 同上 | 抽象出采集层接口，保留替换能力；不把业务逻辑写进 SDK 回调 |
| 识别错误导致报错价 | 中 | 直接资损 + 客诉 | 第 5 节全套拦截规则；宁可转人工 |
| 消息积压 | 中 | 回复超时 | 队列 + 并发消费 + 积压告警 |
| 合规 | — | 违反微信个人账号规范 | 甲方已知悉并接受；建议同步准备企微作为长期迁移路径 |

> **必须明确写上的一句**：个人微信跑自动化违反微信个人账号使用规范，封号是概率事件而非可能性事件。任何"绝对不封号"的承诺都是不成立的。

## 7. 分阶段实施建议

| 阶段 | 目标 | 验收标准 | 粗估 |
|---|---|---|---|
| **P0 可行性验证** | 跑通最窄链路：群消息接入 → 图片原图下载 → 单张截图识别 → 回文本 + 图 | 在真实群里完成 10 单闭环 | 3-5 人日 |
| **P1 识别准确率** | 建立真实截图标注集（建议 ≥200 张），双通道 + 算术闭环上线 | 标注集上金额字段准确率达标，错误全部被拦截而非误发 | 5-10 人日 |
| **P2 稳定性** | 幂等、转人工、留痕、限速、告警 | 连续运行 7 天无重复报价、无漏单 | 5-8 人日 |
| **P3 运营化** | 价目表配置、对账报表、多群管理 | 甲方可自行维护规则 | 5-8 人日 |

**P0 是决策点**：如果 P0 阶段发现协议层登录不稳、或截图识别率达不到要求，应及时止损，不要继续投入。
